# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Energy-aware UAV coverage path planning for scanning outdoor structures (e.g. wind turbines), built on the CTU-MRS UAV stack (ROS1/catkin, Gazebo simulation). This directory (`semestral-project`) is `src/semestral-project` inside a larger catkin workspace rooted at `/home/david/user_ros_workspace/` — it is not a standalone buildable checkout; the workspace's other `src/` packages (`mrs_uav_core`, `mrs_lib`, `mrs_msgs`, gazebo simulation, etc.) must already be present as sibling packages for a build to succeed.

Demo video: https://youtu.be/lA2REzf3Iso

## Build & run

```bash
./run.sh [-c] <world_name>       # -c cleans the catkin workspace first; world_name is a Gazebo world in ~/user_ros_workspace/worlds/
```

`run.sh` runs `catkin build` for the local packages, computes world bounds/spawn position via an external `worldbounds` binary, exports them as env vars (`SPAWN_POSITION`, `ZONE_X`, `ZONE_Y`, `ZONE_Z`), then hands off to `tmux/start.sh`, which launches a `tmuxinator` session (`tmux/session.yml`) with windows for roscore, Gazebo, drone spawn, the MRS UAV core/control stack, the mapping+planning pipeline (`mapplan.launch`), takeoff, and RViz.

To build just this project's packages manually (from the catkin workspace root):
```bash
catkin build octomap_planner_utils frontier_detection prm_solver tsp_solver mrs_octomap_planner mrs_octomap_mapping_planning
```
do not build the project, testing is done manually

There is no test suite (`CATKIN_ENABLE_TESTING` is explicitly disabled in the CMakeLists of the nodelet/library packages, `mrs_octomap_planner`, `frontier_detection`, `prm_solver`, and `tsp_solver`) and no linter is configured.

### Runtime tuning

Most planner behavior is tunable without rebuilding via [ros_packages/mrs_octomap_planner/config/explorer.yaml](ros_packages/mrs_octomap_planner/config/explorer.yaml) (planning distances, frontier/viewpoint sampling, timer rates), [ros_packages/prm_solver/config/prm_solver.yaml](ros_packages/prm_solver/config/prm_solver.yaml) (zone sizes, PRM parameters, its own update timer rate), and [ros_packages/tsp_solver/config/tsp_solver.yaml](ros_packages/tsp_solver/config/tsp_solver.yaml) (TSP duration).

## Architecture

Six ROS packages. `mrs_octomap_planner`, `frontier_detection`, `prm_solver`, `tsp_solver`, and `mrs_octomap_mapping_planning` are `nodelet`-based catkin packages (built into a shared lib loaded by a nodelet manager, not standalone executables); `octomap_planner_utils` is a plain library package with no nodelet.

- **[octomap_planner_utils](ros_packages/octomap_planner_utils/)** — shared geometry/octomap helper library (namespace `octomap_planner_utils`, header [include/octomap_planner_utils/utils.hpp](ros_packages/octomap_planner_utils/include/octomap_planner_utils/utils.hpp) + [src/utils.cpp](ros_packages/octomap_planner_utils/src/utils.cpp)): types like `AABB`, `color_t`, `path_info_t`, `distance_funcion_t`, and free functions for AABB/point geometry, octomap neighbor keys, and free-space checks (`isFreeSpace`, `intersect`, `makeUnion`/`makeIntersection`, `aabbFromCenter`, `getRand`, etc). Depended on by `mrs_octomap_planner` and `frontier_detection`, both of which fully qualify every use with the `octomap_planner_utils::` prefix (no `using namespace`). `frontier_detection` additionally has its own small [include/frontier_detection/utils.hpp](ros_packages/frontier_detection/include/frontier_detection/utils.hpp)/`src/utils.cpp` in the `frontier_detection` namespace, holding just `frontier_t`/`mean`/`getMinBound`/`getMaxBound` — a distinct, package-local helper, not a duplicate of the shared library.

- **[mrs_octomap_planner](ros_packages/mrs_octomap_planner/)** — the core of the project; everything else is scaffolding around it. It's the `Explorer` nodelet ([src/explorer.cpp](ros_packages/mrs_octomap_planner/src/explorer.cpp)), which runs a periodic state machine (`STATE_IDLE → STATE_MAP_UPDATED → STATE_FRONTIERS_UPDATED → STATE_PRM_UPDATED → STATE_TSP_UPDATED → STATE_WAITING → STATE_FLYING`, see `changeState()`; only `STATE_IDLE`/`STATE_FRONTIERS_UPDATED` are actually reached, since PRM/TSP updates happen out-of-process via the `prm_solver`/`tsp_solver` services below) driven by two ROS timers (`timerMain`, `timerPath`) plus an octomap subscription callback.
  - `astar_planner.hpp`, `planner_template.hpp`, `skleton.cpp` (empty) are unreferenced leftover files, not part of the active build (`CMakeLists.txt` only compiles `explorer.cpp` into `MrsOctomapPlanner_Explorer`). Skeleton-guided viewpoint sampling and the `candidate_viewpoints_out` publisher live directly in `explorer.cpp` (`sourceSkeletonCallback`/`targetSkeletonCallback`/`loadSkeleton`), not in `skleton.cpp`.
  - `Explorer` does not run TSP solving or PRM roadmap/path-search in-process: it drives the standalone `tsp_solver` nodelet over two blocking services (`~set_start_out`/`~solve_out`, called back-to-back from `makePath()`) to get the ordered `geometry_msgs/Point[]` viewpoint tour, then drives the standalone `prm_solver` nodelet (see below) over one blocking service (`~find_simplified_path_out`, also called from `makePath()`) per sub-segment of that tour to get a flyable, simplified path.
  - Nodelet class: `mrs_octomap_planner/Explorer` (see [nodelets.xml](ros_packages/mrs_octomap_planner/nodelets.xml)).

- **[frontier_detection](ros_packages/frontier_detection/)** — a standalone nodelet package (`frontier_detection::Detector`, [src/frontier_detector.cpp](ros_packages/frontier_detection/src/frontier_detector.cpp)) with its own message package (`msg/{Frontier,FrontierArray,Viewpoint}.msg`) built around `FrontierManager`/`FIS` classes ([include/frontier_detection/](ros_packages/frontier_detection/include/frontier_detection/), [src/](ros_packages/frontier_detection/src/)): it subscribes to the octomap, tracker command, and control-manager diagnostics, extracts/splits frontier cells into `FIS` clusters within a local zone around the UAV, samples candidate viewpoints per frontier, and publishes them as `frontier_detection/FrontierArray` on `frontiers_out`. Frontier removal (once a frontier is no longer valid) is handled entirely inside `FrontierManager::removeFrontiers()` via `isStillFrontier()` — there is no consumer-driven removal-by-id feedback channel. `mrs_octomap_planner`'s `Explorer` nodelet (`callbackFrontiers()` in explorer.cpp, only to flag that a TSP re-solve is due), the `prm_solver` nodelet (for roadmap node insertion, see below), and the `tsp_solver` nodelet (for TSP ordering) all independently subscribe to this feed on `~frontiers_in`, remapped to `frontier_detection/frontiers`. **The nodelet's own launch include is currently commented out** in [mapplan.launch](ros_packages/mrs_octomap_mapping_planning/launch/mapplan.launch) (lines ~164-171) — it's instead started from [tmux/session.yml](tmux/session.yml) (`roslaunch frontier_detection detector.launch`).

- **[prm_solver](ros_packages/prm_solver/)** — a standalone nodelet package (`prm_solver::PRMNodelet`, [src/prm_nodelet.cpp](ros_packages/prm_solver/src/prm_nodelet.cpp)). The `PRM` class itself ([include/prm_solver/prm.hpp](ros_packages/prm_solver/include/prm_solver/prm.hpp) + [src/prm.cpp](ros_packages/prm_solver/src/prm.cpp)) builds/prunes a roadmap over the octomap (nodes added/aged/invalidated over time) and does A* graph search across it (`findPath`); `findSimplifiedPath()` wraps `findPath()` with a forward+reverse `simplifyFreeSpacePath()` pass. Unlike `frontier_detection`/`tsp_solver`, `addNode`/`updateZone` are **not** exposed to `Explorer` at all — they're driven purely by the nodelet's own subscriptions: `updateZone(..., map_update=true)` runs on every new octomap it receives (own `~octomap_in`/`~tracker_cmd_in`/`~diagnostics_in` subscriptions, mirroring `frontier_detection`'s self-contained position tracking), `updateZone(..., map_update=false)` runs on its own timer (`timer_rates/update` in [config/prm_solver.yaml](ros_packages/prm_solver/config/prm_solver.yaml)), and `addNode` runs for every viewpoint in every `frontier_detection/frontiers` message it receives (not just newly-added ones). The only externally-callable entry point is the `~find_simplified_path_in` service (`FindSimplifiedPath.srv`), called by `Explorer::makePath()`. `PRM`'s other methods (`simplifyRaycastPath`, `distance`, `extraDistance`) are dead code, not wired up to anything. Like its siblings, it's started from [tmux/session.yml](tmux/session.yml) (`roslaunch prm_solver prm_solver.launch`), with a matching commented-out include in `mapplan.launch`.

- **[tsp_solver](ros_packages/tsp_solver/)** — a standalone nodelet package (`tsp_solver::Solver`, [src/solver_nodelet.cpp](ros_packages/tsp_solver/src/solver_nodelet.cpp)). The `TSPsolver` class itself ([include/tsp_solver/tsp_solver.hpp](ros_packages/tsp_solver/include/tsp_solver/tsp_solver.hpp) + [src/tsp_solver.cpp](ros_packages/tsp_solver/src/tsp_solver.cpp)) orders viewpoints into a global visiting path, using a fixed **Euclidean** distance metric between viewpoints, independent of `prm_solver`'s PRM (a PRM-aware metric would require either exposing a distance service on `prm_solver` for `tsp_solver` to call, or moving the metric back in-process). It shells out to the bundled **LKH** TSP solver binary ([ros_packages/tsp_solver/LKH/LKH](ros_packages/tsp_solver/LKH/)) by writing a cost matrix/params file and reading back `solution.txt` (paths resolved via `ros::package::getPath("tsp_solver")`); falls back to greedy/random construction otherwise. The nodelet subscribes directly to `frontier_detection`'s `~frontiers_in` (`frontier_detection/frontiers`) to keep `TSPsolver`'s internal distance graph in sync (`syncFrontiers()`), and to `Explorer`'s `~candidate_viewpoints_in` (`candidate_viewpoints`, a `sensor_msgs/PointCloud2` of skeleton-derived guiding viewpoints) to feed `TSPsolver::setKDtreeInput()`. It exposes `TSPsolver::setStart()`/`solve()` as two ROS services, `~set_start_in`/`~solve_in` (`SetStart.srv`/`Solve.srv`), called by `Explorer::makePath()`. Like `frontier_detection`, it's started from [tmux/session.yml](tmux/session.yml) (`roslaunch tsp_solver tsp_solver.launch`), with a matching commented-out include in `mapplan.launch`.

- **[mrs_octomap_mapping_planning](ros_packages/mrs_octomap_mapping_planning/)** — thin integration package: no source of its own, just the top-level launch file [launch/mapplan.launch](ros_packages/mrs_octomap_mapping_planning/launch/mapplan.launch) that wires together the PointCloud filter (`mrs_pcl_tools`), the Octomap Server, this project's Octomap Planner, the Octomap RViz visualizer, and a nodelet manager. Its dependencies (`mrs_octomap_server`, `mrs_octomap_tools`, `mrs_subt_planning_lib`) are external MRS repos pulled in via `gitman` (see [.gitman.yml](ros_packages/mrs_octomap_mapping_planning/.gitman.yml)), not vendored in this repo.

### Data/control flow at runtime

1. Octomap server publishes an incremental octomap → `Explorer::callbackOctomap` ingests it (for `Explorer`'s own emergency-collision checks); the `prm_solver::PRMNodelet` and `frontier_detection::Detector` nodelets independently subscribe to the same octomap topic for their own purposes.
2. Frontiers are extracted out-of-process by the `frontier_detection::Detector` nodelet and published on `frontier_detection/frontiers`. `Explorer::callbackFrontiers` consumes it only to flag that a TSP re-solve is due, state → `FRONTIERS_UPDATED`; `prm_solver::PRMNodelet` independently consumes the same topic to insert a roadmap node per frontier viewpoint (`addNode`); `tsp_solver::Solver` independently consumes it to keep its own TSP distance graph in sync.
3. `prm_solver::PRMNodelet` updates its PRM roadmap against the current map on its own: `updateZone(..., map_update=true)` on every new octomap it receives, `updateZone(..., map_update=false)` on its own timer — both entirely internal to `prm_solver`, not driven by `Explorer`.
4. Periodically, `Explorer::makePath()` calls the `tsp_solver` nodelet's `~set_start_out`/`~solve_out` services; `TSPsolver` computes a global ordering across all current viewpoints (LKH, with cost matrix built from Euclidean distances and a heading-change penalty) and returns the ordered tour. `makePath()` then steps through that tour in chunks, calling the `prm_solver` nodelet's `~find_simplified_path_out` service per chunk to get a flyable, simplified sub-path from the roadmap.
5. `timerPath` drives the drone toward the nearest/next viewpoint along the assembled path, validating the trajectory is still viable as the map updates, and publishes trajectory references via `mrs_msgs`/`mrs_uav_core` services.
6. Visualization: frontiers (transparent color-coded cubes), viewpoints (pink cubes), and the global TSP path (green lines) are published via `mrs_lib::BatchVisualizer` and viewed in the RViz "explorer" tab; the PRM roadmap (nodes/edges) is published separately by `prm_solver` on its own `visualize_prm` `BatchVisualizer`.

### Simulation stack (tmux/)

[tmux/session.yml](tmux/session.yml) defines the full simulation session: `roscore` → Gazebo world spawn → drone spawn → `mrs_uav_px4_api` (hw_api) → `mrs_uav_core` → `mapplan.launch` → autostart/takeoff → RViz. Per-node config overrides live in [tmux/config/](tmux/config/) (octomap server/filters, network, world, hw_api). `tmux/rviz.rviz` is the RViz layout used for visualization (frontiers/viewpoints/path/trajectory).

## Notes for future changes

- `mfile.txt` and `temp.txt` at the repo root are scratch/leftover files (a stray CMakeLists snippet and commented-out dead code), not part of the build — don't treat them as documentation.
- Prefer editing `explorer.yaml` over hardcoding tunable parameters in C++ when adding new configurable behavior, consistent with the rest of the planner.
- `frontier_detection`, `prm_solver`, and `tsp_solver` each have a launch include in `mapplan.launch` that is currently commented out; all three are actually started from `tmux/session.yml` instead.
